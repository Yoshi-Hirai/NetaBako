# Architecture - Ver0.1

## 1. 目的

NetaBako Ver0.1では、「投稿したい」と思った瞬間に、短い感想からX向け投稿文を生成し、短時間で投稿可能な状態まで進める体験を最優先する。

そのため、初期段階ではシステムを必要以上に分割せず、構成をできるだけ小さく保つ。

将来の拡張性よりも、まず実際に使えるものを早く作り、自分自身で利用しながら仕様と技術構成を見直すことを優先する。

---

## 2. 基本方針

Ver0.1では、以下の方針で開発する。

- モバイル利用を前提とする
- 最初はWebアプリとして実装する
- フロントエンドとバックエンドを別プロジェクトに分割しない
- データベースは使用しない
- ユーザー認証は実装しない
- X APIによる直接投稿は行わない
- ネイティブスマートフォンアプリは最初から作らない
- AI処理に必要なAPIキーはブラウザ側へ公開しない
- 実際に使って必要性が確認できた技術だけ追加する

---

## 3. 初期技術構成

### 言語

TypeScriptを使用する。

フロントエンドとサーバー側処理を同じ言語で扱い、初期開発時の構成と認知負荷を小さくする。

### Webフレームワーク

Next.jsを使用する。

Next.js内で、

- Reactによる画面
- サーバー側処理
- AI APIとの通信

をまとめて実装する。

Ver0.1では、フロントエンドと独立したAPIサーバーは作成しない。

### UI

Reactを使用し、スマートフォンでの利用を前提としたモバイルファーストのUIとする。

PCでも利用可能とするが、主な評価対象はスマートフォンでの操作性とする。

### AI

外部のLLM APIを利用する。

AI APIの呼び出しはNext.jsのサーバー側から行い、APIキーをブラウザへ渡さない。

利用するLLMサービスやモデルについては、実装開始時点で用途、費用、開発しやすさを比較して決定する。

---

## 4. 初期システム構成

Ver0.1の最初の構成は以下とする。

```text
Smartphone / PC Browser
          |
          v
      Next.js
   +-------------+
   | React UI    |
   |             |
   | Server API  |
   +-------------+
          |
          v
       LLM API
```

初期段階では、以下の外部コンポーネントを持たない。

- DB
- Redis
- 独立したGo API
- 認証サービス
- X API
- バックグラウンドジョブ

---

## 5. 最初の実装対象

最初に実装する操作フローは以下とする。

```text
URLを入力
↓
短い感想を入力
↓
投稿文を生成
↓
生成された文章を編集
↓
コピー
```

最初からスマートフォンの共有機能や写真入力まで実装しない。

まずこの最小フローを完成させ、

「自分の一言から、実際に投稿したくなる文章を生成できるか」

を確認する。

---

## 6. URLの扱い

最初の実装では、ユーザーがURLを手入力または貼り付ける。

将来的には、URLから以下の情報を取得し、投稿文生成の参考情報として利用する。

- ページタイトル
- 本文
- ページの概要
- 元URL

ただし、Webサイトによっては本文取得が困難な場合がある。

すべてのWebサイトから完全に本文を取得することをVer0.1の必須条件とはしない。

URL取得処理の複雑さによって投稿文生成の検証が遅れる場合は、最初はURLとユーザーの感想だけをAIへ渡す方式も許容する。

---

## 7. データ保存

Ver0.1の初期実装では、データベースを使用しない。

以下の情報は原則として、その操作中のみ保持する。

- URL
- ユーザーの感想
- 生成された投稿文

投稿が完了した後にデータが失われても問題ないものとする。

これは、Ver0.1が「ネタを保存する箱」ではなく、「その場で投稿まで進めるツール」であるためである。

投稿候補の保存や履歴管理が必要になった場合に、初めてデータベース導入を検討する。

---

## 8. 認証

Ver0.1ではログイン機能を実装しない。

最初の利用者は開発者自身であり、複数ユーザーへの提供を前提としない。

外部公開や第三者利用を開始する段階で、必要に応じて認証方式を検討する。

---

## 9. スマートフォン対応

### 基本方針

最初からiOSアプリ・Androidアプリを個別に開発せず、スマートフォンのブラウザで利用できるWebアプリとして開発する。

主な利用端末としてiPhoneとAndroidの両方を想定する。

### iPhone

初期段階では通常のWebアプリとして利用する。

想定フローは以下。

```text
Web記事を開く
↓
URLをコピー
↓
NetaBakoを開く
↓
URLを貼り付け
↓
一言入力
↓
投稿文生成
```

この操作を実際に利用し、URLコピー・貼り付けの手間が許容できるか確認する。

### Android

初期段階ではiPhoneと同様にWebアプリとして利用する。

将来的にはPWA化し、Androidの共有機能からNetaBakoへURLや画像を直接渡せる構成を検討する。

---

## 10. PWA

PWA対応は初期実装の必須要件とはしない。

基本的な投稿生成フローが成立した後、スマートフォンからの利用を改善するために導入を検討する。

特にAndroidでは、ブラウザや他アプリからNetaBakoを共有先として利用できる状態を目指す。

一方、iOSではAndroidと同じ共有受信方式を利用できるとは限らないため、PWAだけですべてのスマートフォン体験を解決しようとしない。

---

## 11. ネイティブアプリ

React Native / Expoなどによるネイティブアプリ開発は、Ver0.1の初期段階では行わない。

以下のような課題が実際の利用で明確になった場合に検討する。

- iPhoneで共有操作が大きな負担になる
- 写真共有がWebアプリでは使いにくい
- OSの共有メニューから直接NetaBakoを起動したい
- Webアプリでは実現困難なスマートフォン機能が必要になる

ネイティブ化は最初からの前提ではなく、実際の利用結果から必要性を判断する。

---

## 12. 写真対応

写真入力は、URLによる投稿生成フローが成立した後に実装する。

想定フローは以下。

```text
写真を選択または共有
↓
短い感想を入力
↓
AIが写真内容を認識
↓
感想を中心に投稿文を生成
↓
投稿
```

画像認識についても外部AI APIの利用を想定する。

写真をXの投稿画面まで直接引き継ぐ方法については、Webアプリ・PWA・ネイティブアプリそれぞれの制約を確認した上で判断する。

---

## 13. Goバックエンド

Ver0.1の初期段階では、Goによる独立したバックエンドAPIは作成しない。

Next.js内のサーバー処理で十分な間は、その構成を維持する。

以下のような要件が発生した場合にGo APIの導入を検討する。

- 複雑なバックエンド処理が増えた
- 非同期処理やバッチ処理が必要になった
- DBアクセスや外部サービス連携が増えた
- Webフロントエンドとは独立してAPIを提供したくなった
- 負荷や運用面で分離するメリットが明確になった

得意な技術であることだけを理由にGoを追加しない。

---

## 14. ホスティング

ホスティング先は初期実装時点では固定しない。

Next.jsを簡単に公開でき、スマートフォンから実機確認できる環境を優先する。

最初の目的は本番運用環境を完成させることではなく、自分自身が外出先から利用できる状態を作ることである。

利用者増加、独自ドメイン、運用コストなどは、Ver0.1の利用検証後に判断する。

---

## 15. テスト

初期段階では、テストを過剰に作り込まない。

一方で、AIへの入力生成など、仕様が明確でロジックとして検証しやすい部分についてはテスト可能な構造にする。

最優先する確認は実機での操作確認とする。

特に以下を確認する。

- スマートフォンで入力しやすい
- 投稿文生成まで迷わず進める
- 投稿文が編集しやすい
- コピー操作が簡単
- 投稿までの時間が長すぎない

---

## 16. 開発ステップ

### Step 1：画面を作る

Next.jsプロジェクトを作成し、以下を表示する。

- URL入力欄
- 感想入力欄
- 投稿文生成ボタン
- 投稿文表示・編集欄
- コピーボタン

この時点ではAI連携を行わず、ダミーの投稿文表示でもよい。

### Step 2：AI連携

LLM APIを接続し、

```text
URL + ユーザーの一言
↓
X向け投稿文
```

を生成できる状態にする。

### Step 3：スマートフォン確認

外部からアクセスできる環境へ配置し、iPhone・Androidから実際に利用する。

### Step 4：URL内容取得

必要性を確認した上で、URL先の情報をAIへ渡せるようにする。

### Step 5：共有機能

Androidを中心に、共有メニューからNetaBakoへURLを渡す方法を検討する。

### Step 6：写真対応

画像入力・画像認識・写真共有を追加する。

---

## 17. 技術選定の判断基準

新しい技術やコンポーネントを追加する際は、以下を判断基準とする。

1. 現在のユーザー体験上の問題を解決するか
2. Ver0.1の完成を早めるか
3. 実際に必要性が確認されているか
4. 構成を不必要に複雑にしないか

「将来必要になるかもしれない」という理由だけでは追加しない。

---

## 18. 現時点の技術構成まとめ

| 項目           | 方針                    |
| -------------- | ----------------------- |
| 言語           | TypeScript              |
| Web Framework  | Next.js                 |
| UI             | React / Mobile First    |
| Backend        | Next.js内のサーバー処理 |
| AI             | 外部LLM API             |
| Database       | 使用しない              |
| Authentication | 実装しない              |
| X API          | 使用しない              |
| Native App     | 初期段階では作らない    |
| PWA            | 利用検証後に検討        |
| Go Backend     | 必要性が出た場合に検討  |
| Hosting        | 初期実装後に選定        |
